## 2. CMAC: use Node, not a new dependency

**Owner decision (22 Nov):** use the documented `node:crypto` `createMac('CMAC', key, { cipher: 'aes-128-cbc' })` API for the MAC operations. Node [v24.22.3 documentation](https://nodejs.org/download/release/v24.22.3/docs/api/crypto.html#cryptocreatemacalgorithm-key-options) records introduction in **24.22.0** and marks this API **release candidate (stability 1.2)**. This is an in-process OpenSSL-backed API, not shelling out to OpenSSL, using HMAC as a substitute, or implementing RFC 4493 by hand.

- At `092fabde`, builder and runtime in `deployment/Dockerfile` both use floating `node:24-bookworm-slim`; the lockfile resolves `@types/node` 24.19.2, which did not declare `createMac` in the earlier inspection. On 21 Nov a guarded macOS capability probe of the checksum-verified **24.22.3** binary (OpenSSL 3.5.9) reported `createMac: function`, CMAC and AES-128-CBC available, exit 0, no remaining PIDs. Local Node 24.14.0 lacked the API. The historical temp receipt is no longer available; no runtime or vector probe was rerun in this docs refresh.
- For real verification, review an exact patched Node 24 release at or above **24.22.0**, pin the reviewed build/runtime image identities, align the TypeScript declarations, and run the vectors on that exact target. The floating tag and macOS capability probe are not runtime approval. No base image change, package install or silent fallback here. If the API stability or exact target is unacceptable, Auth can review a pinned dependency instead; use the labelled verifier fixture meanwhile.
- Viable package candidate, **not installed**: npm latest `@noble/ciphers@2.4.0`, MIT, no runtime dependencies, Node >=20.19.0, existing **transitive** lock entry, actual `cmac` export in `@noble/ciphers/aes.js`. [Maintainer release](https://github.com/paulmillr/noble-ciphers/releases/tag/2.4.0) published 2026-08-27. ## 3. Mechanism and browser flow

1. **Issue before delivery.** Inventory a personalized inlay under an unpredictable public card ref, then staff binds it to the immutable account in a separate POST with the verified fulfillment record. No first-presenter claim, UID-only fallback, or member-editable binding. Confirm the immutable buyer account, authoritative membership/fulfillment eligibility and the order's recorded rule version through the owning Auth/commerce projection. Book-only and Ticket/invitation-only buyers do not gain a membership card by paying or tapping. Pending or unknown grants must not be presented as issued. A refund or suspension changes the membership state independently; a card's authenticity confers no entitlement.
2. **Verify AES SUN/SDM v1.** The exact URI is `https://sophomores.co/nfc/<22-character unpadded base64url ref>?picc=<32 uppercase hex>&cmac=<16 uppercase hex>`. The 16-byte public ref selects the trusted card snapshot; it is not a UID, secret or account ID. Reject noncanonical size, encoding, case or query order, unknown profiles and inactive refs/epochs. See the fixed file layout below. Use AES-128-CBC with a zero IV and no padding; require exactly `C7 || UID[7] || counterLE[3] || random[5]` from the 16-byte encrypted PICC block. Derive the session key from full AES-CMAC over `3CC300010080 || UID[7] || counterLE[3]`; authenticate the file byte range below and retain zero-based indexes 1, 3, ..., 15 in order. Compare equal-length MACs in constant time, then check the trusted inventory UID. See [the NXP datasheet](https://www.nxp.com/docs/en/data-sheet/NT4H2421Gx.pdf) section 9.3 and [AN12196 rev 2.0](https://www.nxp.com/docs/en/application-note/AN12196.pdf) section 3.
3. **Inspect the tap, then redirect.** The bodyless `GET /nfc/[ref]` handler verifies the exact SUN URI using the canonical member session without renewal or expired-session cleanup. On a valid own-card tap it writes only a two-minute handoff, sets a Secure, HttpOnly browser-binding cookie, and sends a private 303 to a clean document. It stores the verified card, epoch and counter, not the SUN URI. The document reads without writing. Signed-out visitors sign in and re-tap; foreign, unbound, revoked and invalid cards get the same generic unavailable state. Signet status comes from an authoritative read or is unavailable. HEAD, OPTIONS and speculative requests never spend proof.
4. **One explicit Confirm POST.** Submit the opaque handoff ID in the native form to the query-free card path. Require the exact Origin, a valid signed-in member and the matching browser cookie. Consume the handoff, recheck account eligibility, binding, epoch and high-water, then advance the counter and claim the unique Welcome marker in one transaction. The first confirmed tap redirects to `/welcome` (optional passkey); later taps redirect to membership. No tap binds a card, creates a passkey, grants a Signet or Ticket, moves a Safe or checks anyone in.
5. **Keep proof out of follow-on URLs and logs.** Verification proves an authentic tag read, not proximity or MFA. The form response is private/no-store with origin-only referrer policy to support native same-origin POST without forwarding the SUN query. POST redirects are 303, private/no-store and no-referrer. Ingress access/error log redaction and actual browser behavior need separate evidence. Accept counter gaps and an authentic final `FFFFFF` once; never reset, wrap or lower a live epoch fence.

### Fixed wire profile for file 02h

- File-relative offsets are zero-based from **NLEN**, not from the URI or its expanded scheme. Exact template: hex `00 69 D1 01 65 55 04` followed by ASCII `sophomores.co/nfc/<ref>?picc=<32 ASCII zeros>&cmac=<16 ASCII zeros>`. NLEN is 105 bytes; this is one short well-known type-`U` URI record, payload length 101, prefix byte `04` for `https://`, and 107 file bytes including NLEN. Keep the literal punctuation and field widths.
- `PICCENCDataOffset = SDMMACInputOffset = 53` (`35 00 00` LE); `SDMMACOffset = 91` (`5B 00 00` LE). Authenticate bytes `[53, 91)`: the 32 ASCII mirror characters followed by literal `&cmac=`. Do not enable encrypted-file-data mirroring. AN12196 Table 5 instead MACs ASCII **encrypted file data** plus `&cmac=`; its published result checks the vendor primitive, not this application profile. The application fixture has its own independently calculated full and truncated MAC.
- The URI has **no epoch field**. Resolve only the active epoch and its exact keys, with **no old-key fallback**. Every fresh fence for the same ref/UID requires independently derived new file-read MAC key material before the new epoch accepts any proof. NXP section 9.3.1 says enabling SDM via `ChangeFileSettings` resets the hardware counter: never re-enable SDM or otherwise reset under reused MAC keys. Retire the prior epoch before offline reset/reprovision and publish the new epoch only after readback with new keys. One unused old-key tap must fail even with a fresh fence; a proof accepted by the verifier before rotation must fail consumption once rotation commits. Use the same row lock or guarded compare-and-advance predicates for tap, revoke and rekey.
