## What was built

- **Offline QR verification**, in `src/lib/commerce/door/qr.ts`.
  - It reads `data` and `sig` from the scanned URL and ignores the host.
  - It runs viem's `verifyMessage` over the exact `data` string, never re-serialised.
  - It accepts only signers pinned in `UNLOCK_QR_SIGNERS`, a comma-separated list where earlier signers stay valid.
  - It makes no chain, Locksmith or network call.
- **Key to admission**, in `src/lib/commerce/door/check-in.ts`.
  - It maps `network + lockAddress + tokenId` to one admission through the `commerce-key-grant-intents` row that holds the token: `target.chainID`, `target.lock`, `tokenID`, then `entitlement`.
  - It is refused when the chain is not in `keyGrantChains`, when no intent holds the token or lock, or when the intent is not `granted`.
- **One check-in**: `checkInGuest` in `src/lib/commerce/guests.ts` was extended, not duplicated.
  - It takes the same `order-benefits` then `admission` advisory locks as every benefit.
  - A repeat returns `already-checked-in` with the first `checkedInAt` and changes nothing.
  - It refuses with a code: `refunded` (the transaction is refunded or cancelled), `revoked`, `held` (benefit review, an accepted return, or a payment review hold), or `unassigned` (no guest name, claimed account or buyer seat).
  - The admin "check-in" operation calls the same function.
- **Door action**: `doorCheckIn` covers both methods.
  - Resolution, check-in and the attempt log run in one transaction.
  - If the attempt throws unexpectedly, it rolls back, a `refused/error` row is logged in a fresh transaction, and the error is rethrown.
- **Append-only attempt log**: `src/payload/collections/commerce-door-attempts/`.
  - Fields: operator, event, admission, method `qr|name`, result `admitted|already-checked-in|refused`, reason code, tokenID and `attemptedAt`.
  - Hooks refuse every update and delete, even with `overrideAccess`.
  - Read access is super-admin only, through `ledgerCollection`.
- **Migration**: `src/payload/migrations/20261115_205007_door_attempts.{ts,json}`, one additive migration.
  - It was generated by `payload migrate:create` under `env -i`, with a placeholder `DATABASE_URI`.
  - By hand, I reordered `down` to drop constraints before the table, with `IF EXISTS`, and normalised the whitespace.
  - `src/payload-types.ts` was regenerated; the diff contains only door additions. `src/payload-generated-schema.ts` was not regenerated.
- **Name fallback**: `searchDoorAdmissions`.
  - It searches the event's admissions by guest name, or by member name for claimed or buyer-own seats.
  - Matching is NFC, case-insensitive and by substring, capped at 20 results.
  - Confirming a result calls `doorCheckIn` with method `name`.
- **Running count**: `doorCount`, checked in out of available, claimed and checked-in admissions.
- **Endpoints**, in `src/lib/commerce/door/endpoints.ts`, registered by the commerce domain plugin:
  - `POST /api/commerce/door/check-in`
  - `GET /api/commerce/door/events/:eventID/search?q=`
  - `GET /api/commerce/door/events/:eventID/count`

  All three require `isCmsStaff`. The POST also requires a JSON body, under 8 KiB, from the same origin; the staff session is a cookie.
- **The door page** is at `/admin/door`: `src/payload/admin/door/door-view.tsx` (server) and `door-console.tsx` (client).
  - It has an event picker, the running count, and the outcome card (admitted, already checked in with time, refused with reason, not found, and a retryable failure).
  - Scanning uses camera scanning through `BarcodeDetector` where it exists. A text field is always present for a pasted link or a hardware scanner.
  - It also has name search with a check-in on each row.
  - It is Tailwind only, with the existing `staff:` prefix; `@source` was added in `src/styles/staff-login.css`.
  - Every control is at least 48 px.
  - Copy lives under `Staff.door` in `messages/en.json`. `messages/ko.json` mirrors it with `""`, and the structure check passed.
- **Card-tap seam.** A member card tap resolves its admission, then calls `doorCheckIn` with a third method. The method enum and `checkInGuest` are already shared, and nothing card-specific was built.

### Why the page is a Payload admin view

Every existing staff surface is a Payload admin component under `src/payload/admin/`: the commerce operation panels, the event manifest, recovery review and staff login. They all sit behind the same CMS staff sign-in (`admins`, `staff-better-auth`). The door view joins them, so door staff use the one staff sign-in. The server component and every endpoint check `isCmsStaff` independently.

## Behaviour changes to existing code (please review)

- **`checkInGuest`**, the existing admin "check-in" operation:
  - It now accepts any CMS staff role (`isCmsStaff`); before, only super admins could use it. This follows ADR-0007, which says door staff are CMS staff.
  - It now admits a member's claimed seat or the buyer's own seat with no `guestName`. Before, a guest name was required. A seat with no holder is refused as `unassigned`.
  - It now returns `already-checked-in` before checking holds. A used admission whose order was later held or refunded reports when it was used, instead of throwing "held".
  - It returns `{ outcome, checkedInAt }` instead of `void`. The admin endpoint still answers `{ success: true }`.
- **`tests/support/database-proof.mjs`** gained `--only=<file>`.
  - A full run force-removes every proof's container by name, which would remove other workers' live containers.
  - So I ran only the door proof; the full launcher was not run.
- **`src/lib/commerce/domain.ts`** registers the collection, the door endpoints and the `door` admin view.
- **`src/app/(payload)/admin/importMap.js`** was regenerated (`generate:importmap`). Only the door view was added.

## Known limits and dependencies

- **Real guest QRs cannot map yet.**
  - The key-grant intents collection still refuses `recipientMode: "guest_email"` ("Guest key grants are not enabled yet").
  - Until guest key grants ship, every real guest QR resolves to `unknown-token`. The page shows "Not found", and staff fall back to name search.
  - The tests and render use `member_safe` intents.
  - Unlock emails a QR only when the lock carries event metadata (`unlock-qr-verification.md`). Both are upstream dependencies.
- **Signers must be configured.**
  - With `UNLOCK_QR_SIGNERS` unset, every QR is refused as `unpinned-signer`.
  - The research doc's observed signer, `0x22c0…2f4C`, was seen on Base (8453). `keyGrantChains` is `[137, 84532]`.
  - The owner needs to supply the Locksmith signers for the chains actually in use. Nothing is pinned in application configuration.
- **What the codes can tell apart.**
  - `unknown-lock` is only distinguished from `unknown-token` when the token exists on that chain under a different lock.
  - A payload re-serialised after signing is reported as `unpinned-signer`. It recovers to some other address, so it cannot be told apart from a stranger's signature.
  - The test shows that verification uses the exact scanned bytes, because a non-canonical signed payload passes.
- **Signed-out visitors.** Payload does not redirect them from `/admin/door`. They see "Door check-in is for staff. Sign in with a staff account to use it." with no sign-in link (`render/1280-not-staff.png`). The endpoints refuse them independently.
- **iPhone Safari.**
  - WebKit does not ship `BarcodeDetector`, as far as I know. This is not verified on a device.
  - On iPhone the page shows "This browser can't scan with the camera…", and the text field (paste, or a hardware scanner) still works.
  - If in-page camera scanning is wanted on iPhone, the one package to ask the owner about is `jsqr@1.4.0`, published 2021-04-24 (`npm view jsqr time`).
  - No QR library was installed.
