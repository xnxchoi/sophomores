## Launch-event mapping

### Common facts versus proposed commercial resolution

Settled together: this sale bootstraps membership and bought event access (D1/D2 lines 61–64); token holding alone gives no seat; first absent buyer/event occupancy is reserved at settlement, additional/subsequent units are gifts (T001 lines 233–244); one account gets one event package; physical product/fulfillment is not silently removed. The event package remains four Part I drinks plus shared Part I→II transport for the eligible activated account/event (D3/D4 lines 97–100), not five additional NFTs. Event timing and consumption rules remain separate. An unactivated gift consumes sold access even before a recipient is known; the later cancellation decision removes cancelled units from active allowance/capacity without erasing their history.

**Proposed first-sale bundle:** a unit supplies a perpetual membership-token acquisition entitlement **where the eventual account lacks one**, one paid event-access entitlement, the existing event package, and its existing physical fulfillment obligation. Buying/reserving does not prove activation, issuance or attendance. This conditional token acquisition is necessary to avoid double membership but its already-holder commercial treatment is not explicitly settled. Do not publish “one new NFT per purchased unit for its buyer” or silently convert paid token rights to event-only rights.

`settlePaidUnits` receives an already verified paid snapshot under the payment transaction owner. For every valid new snapshot it creates exactly its paid units and event access, binds the first buyer/event self unit if absent, and records the remaining units as gifts. **Even with every optional policy unselected, settlement completes allocation.** Missing already-holder disposition records pending-policy token rights, not a rejection, rollback, 503 or no-effects result. Replay is idempotent. Genuine integrity/transaction failure is still an error requiring existing payment recovery; do not fabricate success for corrupt input or claim captured funds rolled back with a local transaction.

`activateUnit` separately requires canonical account proof, explicit intent, approved timing/receipt eligibility, no holds, and no duplicate event/membership binding. Event completion is never a failing token-activation timing signal; unrelated proof/financial guards still apply. It consumes the validated bearer, binds the same allocated admission, reserves the one account membership slot and records immutable intent data in one commit when a new membership is needed. An explicitly selected existing-holder reuse returns the original membership reference with no new issuance operation. An unresolved existing-holder disposition returns policy-required **for that activation/disposition only**, before consuming the gift; event end alone does not; they never remove paid units. Arrival is the same on-the-spot activation process, whether guest-led, staff-guided or staff-assisted, with no separate name-based check-in command or bypass. An unactivated unit cannot receive attendance success; a prior checked-in flag cannot bypass guest identity, consent or activation. Preserve historical usage for reconciliation rather than treating it as another entry path. Opening, GET, preview, readiness and account switching do not consume; account change invalidates prior intent. Same-account result recovery returns original IDs; other accounts get no private claimant/result.

`assessGiftLinkEligibility` is a read-only decision: an otherwise eligible unactivated, unoccupied gift needs no guestName; legacy checked-in status cannot substitute for guest proof or activation, and financial-held inputs require review. It generates no secret or link; later production wiring must replace the name prerequisite in issueGuestClaim, not leave it as a second gate.

Staff assistance is an actor mode of activateUnit, not another allocation/claim engine: staff role or a typed account ID alone cannot prove the guest’s account/consent. The mechanism is **unselected**, so staff-assisted binding is held unless an explicitly trusted, guest-scoped proof-and-consent fixture is supplied; no actual proof mechanism is chosen here. Guest-led activation remains independently testable. Reliability includes replay-safe same-account result recovery and explicit pending/failure handling, never named-entry fallback or fabricated issuance success when P2b is unresolved.

`regenerateActivationCode` is a buyer-authorized pure decision over an unactivated unit, not a new purchase, allocation or account assignment. **Proposed mechanics:** accept an already generated replacement digest and stable request/version identity; under the same admission lock as activation, rotate to one new capability version, invalidate the prior digest, and preserve immutable self/gift allocation. A duplicate request returns its original version without rotating again; changed replay rejects. If rotation commits first, the old code cannot activate and the new one can; if activation commits first, regeneration rejects without changing the holder/result. No raw code is generated/returned/persisted by this decision function; later approved link delivery must handle secret-loss/retry without inventing more rotations. Staff role alone is not buyer authority.

No return, issuer observation, submission or recovery execution belongs to P2a. It can carry externally supplied financial holds and opaque issuance-intent data without importing P2b. “Activated” means verified binding committed, not minted success. Membership uniqueness is account-wide; event uniqueness is separately event/account-wide.

### Command ownership and lock order — required future integration map

The kernel is a **pure decision function called under the existing command's locks**, followed by that same transaction owner's writes. It never acquires locks or ends transactions itself. Production integration must **replace the corresponding allocation/activation decisions in guests.ts**, not run a new claim engine beside them (T001 lines 242–245). That wiring is not owned by either isolated slice; it needs a separate allowlist and approved schema.

Existing payment adapter order is authoritative: `src/lib/commerce/portone/adapter.ts:100-104` takes preparation/cart resources; `src/lib/commerce/portone/adapter.ts:163-176` locks reservation context before plugin inventory writes to avoid inversion. `src/lib/commerce/reservations.ts:17-30` locks attempt then event/product/allowance resources. Settlement reaches `src/lib/commerce/ecommerce.ts:125-133` in the same payment transaction, then `src/lib/commerce/guests.ts:35-68` takes order-admissions and late event-account. Keep these existing stages; do not acquire an earlier stage after a later one.

**Proposed new terminal ranks:** after all applicable event-account keys, acquire `account-membership:<canonicalAccountID>`, then `issuance-operation:<operationID>` when applicable. Membership and operation keys are terminal: no code holding them may go back for an order, admission, reservation or event-account lock. For batches, gather all immutable targets first and acquire all admissions, then all event-account keys, then all membership keys, then all operation keys; sort/deduplicate within each rank, not lexicographically across ranks. Reread mutable state after locking; if target discovery changes the set, restart from the owner boundary rather than grab an earlier rank. All callers sharing these records must obey this proposed order before production integration; fake scheduling cannot prove it.

#### Fake issuer and deferred contract

Interface proposal: `submit(intent)` and `reconcile(originalIntent, priorObservation)` each return submitted(submissionID), confirmed(credentialReference, evidenceID), verified-not-issued(evidenceID), or unknown(optional submissionID, evidenceID). Require exact immutable operation, account, entitlement, kind and target match; mismatch is an integrity hold. Fake submission ID is not confirmed issuance or a real transaction hash.

1. P2a activation already records complete immutable intent data in its binding commit. P2b derives ready state from that data idempotently; no new identity, bearer use or non-atomic replacement binding is allowed. Dispatch atomically marks submitting plus a stable attempt identity before the call, then releases locks. No issuer call occurs inside the transaction.
2. Timeout/throw/crash after the marker, with or without a returned submission ID, becomes unknown. A reconstructed submitting marker is unknown, not ready. Reconcile the original operation; never replace its operation to escape uncertainty.
3. submitted and unknown allow reconciliation only. Fake issuer includes a deliberately non-idempotent submission mode; tests must prove safety without relying on fake submit deduplication. No automatic submit retry or background timer.
4. Confirmation attaches one stable credential reference; identical receipt replay returns it; conflicting recipient/receipt holds. Fake lookup absence alone is unknown, not nonexecution proof.
5. Only explicit verified-not-issued evidence resolving every previous attempt, with no conflicting confirmation or still-unresolved submission, may permit another dispatch of the same immutable operation. Retain attempt history, recheck holds/proof and allocate no unit/seat/charge/slot.
6. Reconstruct test state from in-memory snapshots after crash; execution before lost receipt must reconcile original credential with exactly one submission. A hold racing success retains confirmed receipt plus review/recovery state, not fictitious revocation by rollback.

B4 lines 200–202's separate membership/event outcomes apply to a later adapter **if** R17 selects a separate event credential. Neither P2a nor P2b issues an event credential or silently chooses that architecture.

#### Policy inputs, returns and settled cancellation release

Fixed product facts remain one/account membership, perpetual/no-expiry token and link, one/event occupancy, paid access and no peer transfer. R05 records the owner's no-refund-before-activation position. **Its enforcement is a separate versioned input, unselected until legal/PG review**: unselected routes a request to review; an explicitly selected owner-refusal fixture denies a voluntary request. No generic “allow refund” switch may invent a legal remedy; an exception needs separately authorized evidence and disposition.

Required policy inputs are already-holder purchase/gift disposition, authorized timing eligibility, staff-assisted guest-account/consent proof, preactivation-refund enforcement and postactivation-return disposition. **Cancellation allowance/capacity release is settled and is not a policy input.** Unselected settlement still allocates and records pending token rights; unselected activation/assistance does not consume its bearer; unselected refund enforcement records review rather than an implemented denial. Verified cancellation always records its evidence and releases its cancelled units from active allowance and event capacity exactly once, regardless of these optional choices.

`requestReturn` separates voluntary money request, physical receipt evidence, activation, usage and provider-confirmed reversal. Physical receipt alone cannot approve refund or delete membership. `src/lib/commerce/returns.ts:31-35` only tests check-in/redemptions for “used”: an activated but not checked-in unit falls into its unused branch and loses event occupancy today. That is not approved token-return policy and cannot be copied to the new model. U3 now allows late activation: neither an unused past-event package nor missing check-in proves the perpetual token is unactivated or refundable; activation and event usage remain independent facts. Preserve both facts and hold the disposition for review.

Cancellation tests must assert the settled deltas, not alternative product policies: each newly cancelled unit reduces active paid purchase allowance and event capacity, with replay/partial prior returns never releasing it twice. This preserves the intended release at `src/lib/commerce/reservations.ts:101-104` and `src/lib/commerce/reservations.ts:117-122`. Remove the prior hold-counter/retention alternative. The current source computes released capacity only for unused admissions (`src/lib/commerce/reservations.ts:115-118`); for a previously used cancelled unit, preserve historical attendance/redemptions but remove its active capacity commitment under the owner’s broad rule. Later schema/wiring must reconcile historical usage separately and prove this without negative counters or double release; do not assert current source already proves that used-unit case.

Event occupancy history and membership/token recovery are distinct from active allowance/capacity. Preserve original paid rows, usage and immutable identity; a cancelled unit cannot restore usable access by replay or late activation. If issuance already succeeded or might have, retain its original receipt/unknown outcome under financial/recovery hold, never a fictitious rollback revocation. Cancellation release is not a voluntary refund approval or token-transfer authorization. Actual token reversal and statutory/PG remedies remain separate; money movement is absent from this fake slice.
