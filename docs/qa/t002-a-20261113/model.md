## Launch-event mapping

### Common facts versus proposed commercial resolution

Settled together: this sale bootstraps membership and bought event access (D1/D2 lines 61–64); token holding alone gives no seat; first absent buyer/event occupancy is reserved at settlement, additional/subsequent units are gifts (T001 lines 233–244); one account gets one event package; physical product/fulfillment is not silently removed. The event package remains four Part I drinks plus shared Part I→II transport for the eligible activated account/event (D3/D4 lines 97–100), not five additional NFTs. Event timing and consumption rules remain separate. An unactivated gift consumes sold access even before a recipient is known.

**Proposed first-sale bundle:** a unit supplies a perpetual membership-token acquisition entitlement **where the eventual account lacks one**, one paid event-access entitlement, the existing event package, and its existing physical fulfillment obligation. Buying/reserving does not prove activation, issuance or attendance. This conditional token acquisition is necessary to avoid double membership but its already-holder commercial treatment is not explicitly settled. Do not publish “one new NFT per purchased unit for its buyer” or silently convert paid token rights to event-only rights.

| --- | --- | --- |

Each sold unit funds one event access/package. Buyer retains all payment/shipping ownership. | **Proposal:** unit 1 also reserves the sole account membership-acquisition slot; token intent is created only by explicit eligible activation. Existing self activation timing (after purchase versus delivery-gated) remains unselected: require an explicit server-authorized eligibility input, not a fabricated delivery signal. |

### Records and immutable invariants

Records below are **logical local types**, not approved collection names or schema changes. IDs are opaque stable fixture values; canonical account ID, never email, owns membership. Store bearer digest only; validated capability/proof enters privately and is never returned in diagnostics.

| Record | Minimum fields and invariant |
| --- | --- |
| Paid unit | `orderUnitID` (existing order:unit identity), order/transaction snapshot identity, event, buyer, provenance self/gift, package rule version, financial state. Settlement replay must match immutable identity and quantity or return integrity-error, not partially regenerate units. |
| Token entitlement | Stable `entitlementID`, source paid unit, optional reserved/activated account, lifecycle unactivated/activated/recovery, optional membership reference, policy version. Event is provenance only, not token lifetime. Gift has no invented account. Reserving self does not activate it. |
| Account membership slot | Unique canonical `accountID`, stable membership identity when known, originating entitlement and issuance operation. Reservation, pending and unknown occupy the slot just as confirmed ownership does. Cross-event concurrent activation cannot allocate another slot. Existing-holder fixture refers to the original membership, never a new operation. |
| Event admission | Stable admission/order-unit/event identity, optional reserved or activated account; unique event/account occupancy; available/claimed/checked-in/revoked plus financial/review hold and package usage. Unclaimed gift still consumes one sold access allocation. Membership and attendance are not this record's status. |
| Issuance operation | Immutable operation ID, entitlement/account target, kind membership, policy/custody version, intended perpetual lifetime and manager-policy reference (logical only), state ready/submitting/submitted/confirmed/unknown/verified-not-issued/held; optional submission ID, confirmed credential reference and evidence identity. One unresolved account operation blocks any second membership operation. |
| Recovery case | Same membership/account/operation references, actor/evidence/reason and unresolved/resolved outcome. Only a synthetic Sophomores-authorized command enters recovery; no account reassignment, peer transfer, new purchase, capacity release or perk reset. |

“Activated” means the explicit verified account binding committed, not confirmed mint. A public success result must distinguish activation-bound/issuance-pending, issuance-unknown and confirmed membership. `recovery` describes an interrupted/controlled same-account process; `unknown issuance` is the operation's evidence state, not permission to reactivate a consumed gift. Preserve both dimensions, not a single conflated enum. Account readiness is an explicit verified input, not a profile membership label or the misleading current `isActiveMember` name (B1 lines 53–57).

One local atomic command validates against a complete immutable input snapshot and produces either a complete replacement state plus effects, or unchanged state and typed rejection. The test store commits with a revision compare-and-swap and reevaluates on conflict; tests explicitly schedule stale reads. This is **synthetic serialization**, not real PostgreSQL uniqueness/race evidence. Production must later map it to the existing transaction owner and prove the same invariant with database constraints/locks; do not add a second payment or claim engine.

Commands: `settlePaidUnits`, `activateUnit`, `recordIssuanceObservation`, `requestReturn`, `beginRecovery`, `resolveRecovery`, and authorized read/result recovery. Every command carries stable command identity and expected immutable target; replay with changed payload rejects. Account/entitlement/event uniqueness commits together with bearer consumption and intent. GET/open/readiness/refresh does nothing. Same-account lost-result recovery returns original references; different-account replay yields no claimant or private result. Financial/shipping ownership never changes on activation.

### Fake issuer interface and deferred issuance

Interface proposal (semantic contract, no provider type): `submit(intent)` returns submitted(submissionID), confirmed(credentialReference, evidenceID), verified-not-issued(evidenceID), or unknown(optional submissionID, evidenceID). `reconcile(originalIntent, priorObservation)` returns the same observation union. All observations must match operation identity, account, entitlement, kind and immutable policy target; mismatches are integrity holds. A fake submission ID is not a confirmation or a real transaction hash.

1. Persist ready intent with activation/binding in one fake-store commit. No issuer call inside that transaction. A dispatch command atomically marks submitting with a stable attempt identity before calling the fake issuer.
2. Timeout/throw/crash after that mark, even without returned submission ID, becomes unknown. Recover the original operation; never create a replacement operation because a response was lost. A persisted dispatch marker found after restart is likewise unknown, not ready.
3. submitted and unknown permit reconciliation only. Fake issuer must deliberately support a non-idempotent scenario so tests cannot accidentally “prove” safety by deduplicating every submission. No automatic submit retry, no polling timer in production kernel.
4. A confirmed observation attaches one stable credential reference to the membership slot. Replay of the same receipt returns that reference; conflicting receipt/recipient causes a hold. Mere fake lookup absence is unknown, not proof of nonexecution.
5. Only explicit verified-not-issued evidence, with no conflicting prior confirmation/submission, can permit another dispatch attempt of the **same immutable operation** under the local contract. Preserve attempt history and revalidate holds/readiness. An unresolved original attempt never qualifies. No new paid unit, seat, charge or membership slot.
6. Persist reloadable fake-store snapshots in test memory: restart reconstruction reads original operations rather than process-local “sent” flags. Crash between fake execution and receipt commit must reconcile to the original credential with exactly one submission. If a hold races confirmed issuance, retain confirmed receipt plus recovery/review hold; do not pretend rollback revoked anything.

B4 lines 200–202's independent membership/event issuance outcomes remain a future adapter requirement **if** a separate event credential is selected. P2 records local event admission without issuing it. Do not manufacture an event grant to satisfy an undecided architecture.

### Returns and recovery boundaries

`requestReturn` distinguishes voluntary refund request, physical-return evidence and authoritative payment reversal. Unactivated voluntary refund is policy-denied with **no** allowance/capacity/slot/bearer changes. Physical receipt alone records evidence, never refund approval. Activated voluntary return is policy-required/manual review unless separately authorized; no default refund, membership deletion, event-key clearing or resale. This deliberately does not copy `returns.ts`'s unused-unit clearing.

Authoritative payment cancellation is not denied by the no-refund product rule: record financial hold/evidence and suppress new dispatch/use; do not erase the membership, original allocation or money history. If issuance already succeeded or might have, retain a recovery case for later authorized reversal policy. Fake tests assert no double release/refund/grant; money movement itself is absent. A recovery command can reconcile the same account/credential only, not grant a new token or transfer it. Actual replacement/revocation and after-activation statutory/PG remedies remain separately approved policy/operations work.
