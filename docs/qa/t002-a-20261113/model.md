## Launch-event mapping

### Common facts versus proposed commercial resolution

Settled together: this sale bootstraps membership and bought event access (D1/D2 lines 61–64); token holding alone gives no seat; first absent buyer/event occupancy is reserved at settlement, additional/subsequent units are gifts (T001 lines 233–244); one account gets one event package; physical product/fulfillment is not silently removed. The event package remains four Part I drinks plus shared Part I→II transport for the eligible activated account/event (D3/D4 lines 97–100), not five additional NFTs. Event timing and consumption rules remain separate. An unactivated gift consumes sold access even before a recipient is known.

**Proposed first-sale bundle:** a unit supplies a perpetual membership-token acquisition entitlement **where the eventual account lacks one**, one paid event-access entitlement, the existing event package, and its existing physical fulfillment obligation. Buying/reserving does not prove activation, issuance or attendance. This conditional token acquisition is necessary to avoid double membership but its already-holder commercial treatment is not explicitly settled. Do not publish “one new NFT per purchased unit for its buyer” or silently convert paid token rights to event-only rights.

These proposals do not reopen D1/D2's allocation rule. They identify the new tension between a sale delivering a token, perpetual one/account membership and a forced-self event purchase by an already-holder. Event-lock selection R17 is independent of this commercial decision. None of these missing policy answers may reject an otherwise verified paid snapshot or suppress its unit/event allocation: blueprint lines 188–189 and `src/lib/commerce/ecommerce.ts:125-133` require allocation in the payment transaction even when captured-money reconciliation is difficult.

#### P2a records and decisions

Logical types, not approved database collections:

| Record | Minimum contract |
| --- | --- |
| Paid unit | Stable `orderUnitID` (order:unit), immutable order/transaction snapshot identity, buyer/event, self/gift provenance, event rule version and financial evidence. Complete replay returns original allocation; mismatched or partial/corrupt historical identity is an integrity error, not permission to regenerate. |
| Token entitlement | Stable entitlement/source-unit IDs; unactivated/activated lifecycle; reserved/activated canonical account when applicable; membership reference if already known; disposition acquisition/reuse/separate-gift/pending-policy. Event is provenance, not token lifetime. Gift has no fabricated recipient. |

| Event admission | Stable unit/event/admission IDs, immutable reserved buyer occupancy or activated claimant; one event/account occupancy; attendance/usage separate from activation and finance. Each sold unit consumes an access obligation, even unactivated. No event credential is assumed. |
| Activation intent data | Stable command/operation/entitlement/account identities and immutable membership target/policy version. Recorded atomically with activation binding and bearer consumption, even before any issuer module exists; it makes no submission or success claim. |
| Policy hold | Reason, affected right/operation, original paid identities and pending decision. A token-disposition hold coexists with completed paid allocation; it never makes settlement a no-op. |

`settlePaidUnits` receives an already verified paid snapshot under the payment transaction owner. For every valid new snapshot it creates exactly its paid units and event access, binds the first buyer/event self unit if absent, and records the remaining units as gifts. **Even with every optional policy unselected, settlement completes allocation.** Missing already-holder disposition records pending-policy token rights, not a rejection, rollback, 503 or no-effects result. Replay is idempotent. Genuine integrity/transaction failure is still an error requiring existing payment recovery; do not fabricate success for corrupt input or claim captured funds rolled back with a local transaction.

`activateUnit` separately requires canonical account proof, explicit intent, approved timing/receipt eligibility, no holds, and no duplicate event/membership binding. It consumes the validated bearer, binds the same allocated admission, reserves the one account membership slot and records immutable intent data in one commit when a new membership is needed. An explicitly selected existing-holder reuse returns the original membership reference with no new issuance operation. Existing holder or late-activation questions return policy-required **for that activation/disposition only**, before consuming the gift; they never remove paid units. Event rules, not a guest name, determine admission eligibility. A checked-in-before-activation historical row returns legacy-activation-review, preserving usage rather than silently legitimizing it. Opening, GET, preview, readiness and account switching do not consume; account change invalidates prior intent. Same-account result recovery returns original IDs; other accounts get no private claimant/result.

`assessGiftLinkEligibility` is a read-only decision: an otherwise eligible unactivated, unoccupied gift needs no guestName; legacy checked-in or financial-held inputs require review. It generates no secret or link; later production wiring must replace the name prerequisite in issueGuestClaim, not leave it as a second gate.

No return, issuer observation, submission or recovery execution belongs to P2a. It can carry externally supplied financial holds and opaque issuance-intent data without importing P2b. “Activated” means verified binding committed, not minted success. Membership uniqueness is account-wide; event uniqueness is separately event/account-wide.

### Command ownership and lock order — required future integration map

The kernel is a **pure decision function called under the existing command's locks**, followed by that same transaction owner's writes. It never acquires locks or ends transactions itself. Production integration must **replace the corresponding allocation/activation decisions in guests.ts**, not run a new claim engine beside them (T001 lines 242–245). That wiring is not owned by either isolated slice; it needs a separate allowlist and approved schema.

Existing payment adapter order is authoritative: `src/lib/commerce/portone/adapter.ts:100-104` takes preparation/cart resources; `src/lib/commerce/portone/adapter.ts:163-176` locks reservation context before plugin inventory writes to avoid inversion. `src/lib/commerce/reservations.ts:17-30` locks attempt then event/product/allowance resources. Settlement reaches `src/lib/commerce/ecommerce.ts:125-133` in the same payment transaction, then `src/lib/commerce/guests.ts:35-68` takes order-admissions and late event-account. Claims take order-benefits → admission (`src/lib/commerce/_shared/benefits.ts:14-17`) → event-account (`src/lib/commerce/guests.ts:66-68`, `src/lib/commerce/guests.ts:148-150`). Keep these existing stages; do not acquire an earlier stage after a later one.

**Proposed new terminal ranks:** after all applicable event-account keys, acquire `account-membership:<canonicalAccountID>`, then `issuance-operation:<operationID>` when applicable. Membership and operation keys are terminal: no code holding them may go back for an order, admission, reservation or event-account lock. For batches, gather all immutable targets first and acquire all admissions, then all event-account keys, then all membership keys, then all operation keys; sort/deduplicate within each rank, not lexicographically across ranks. Reread mutable state after locking; if target discovery changes the set, restart from the owner boundary rather than grab an earlier rank. All callers sharing these records must obey this proposed order before production integration; fake scheduling cannot prove it.

| --- | --- |
| P2a settlePaidUnits / existing payment transaction | Already-held payment preparation/cart and reservation attempt/event/product/allowance context → order-admissions:order → event-account:event/buyer → account-membership:buyer for membership/disposition read. | P2a activateUnit / existing claim or self-activation transaction | order-benefits:order → admission:unit → event-account:event/account → account-membership:account → issuance-operation:stable activation anchor. | P2a assessGiftLinkEligibility / existing gift-link transaction | order-benefits:order → admission:unit, with authoritative reread; no event-account/membership/operation mutation or bearer generation in this pure assessment. |

`lockCommerce` sorts each supplied key set (`src/lib/commerce/_shared/transaction.ts:19-23`), not an entire transaction's acquisition history; rank order therefore requires separate calls. The new membership key sits **after event-account even inside payment settlement**, never before adapter reservation/inventory locks. This map grants no permission to alter transaction ownership or migrate schemas now.

### P2b — fake issuance, unknown outcomes, recovery and returns

**Owned files for a later, separate dispatch:** `src/lib/commerce/token-issuance.ts`; `tests/commerce/domain/token-issuance.test.ts`; `tests/commerce/domain/token-issuance-fixtures.ts`. P2a's module is a read-only dependency; changes to it need a newly explicit allowlist. P2b depends on P2a's stable activation intent records, while P2a works without P2b. No runtime registration or provider integration.

P2b adds issuance states ready/submitting/submitted/confirmed/unknown/verified-not-issued/held, immutable operation/account/entitlement/kind/target and policy/custody versions, intended perpetual lifetime, manager-policy reference, attempt history and optional submission/credential/evidence IDs. Recovery records refer to the same account, membership and original operation, with actor/reason/evidence and unresolved/resolved state. Unknown issuance is not permission to reactivate a consumed gift; recovery cannot transfer, reset benefits or allocate another membership. Independently retain activation, attendance and financial evidence.

#### Fake issuer and deferred contract

Interface proposal: `submit(intent)` and `reconcile(originalIntent, priorObservation)` each return submitted(submissionID), confirmed(credentialReference, evidenceID), verified-not-issued(evidenceID), or unknown(optional submissionID, evidenceID). Require exact immutable operation, account, entitlement, kind and target match; mismatch is an integrity hold. Fake submission ID is not confirmed issuance or a real transaction hash.

1. P2a activation already records complete immutable intent data in its binding commit. P2b derives ready state from that data idempotently; no new identity, bearer use or non-atomic replacement binding is allowed. Dispatch atomically marks submitting plus a stable attempt identity before the call, then releases locks. No issuer call occurs inside the transaction.
2. Timeout/throw/crash after the marker, with or without a returned submission ID, becomes unknown. A reconstructed submitting marker is unknown, not ready. Reconcile the original operation; never replace its operation to escape uncertainty.
3. submitted and unknown allow reconciliation only. Fake issuer includes a deliberately non-idempotent submission mode; tests must prove safety without relying on fake submit deduplication. No automatic submit retry or background timer.
4. Confirmation attaches one stable credential reference; identical receipt replay returns it; conflicting recipient/receipt holds. Fake lookup absence alone is unknown, not nonexecution proof.
5. Only explicit verified-not-issued evidence resolving every previous attempt, with no conflicting confirmation or still-unresolved submission, may permit another dispatch of the same immutable operation. Retain attempt history, recheck holds/proof and allocate no unit/seat/charge/slot.
6. Reconstruct test state from in-memory snapshots after crash; execution before lost receipt must reconcile original credential with exactly one submission. A hold racing success retains confirmed receipt plus review/recovery state, not fictitious revocation by rollback.

B4 lines 200–202's separate membership/event outcomes apply to a later adapter **if** R17 selects a separate event credential. Neither P2a nor P2b issues an event credential or silently chooses that architecture.

#### Policy inputs and returns — pending is not a final accounting choice

Fixed product facts remain one/account membership, perpetual/no-expiry token and link, one/event occupancy, paid access and no peer transfer. R05 records the owner's no-refund-before-activation position. **Its enforcement is a separate versioned input, unselected until legal/PG review**: unselected routes a request to review; an explicitly selected owner-refusal fixture denies a voluntary request. No generic “allow refund” switch may invent a legal remedy; an exception needs separately authorized evidence and disposition.

Required policy inputs are already-holder purchase/gift disposition, late activation, authorized timing eligibility, preactivation-refund enforcement, postactivation-return disposition, and verified-cancellation accounting. Unselected **settlement** still allocates and records pending token rights. Unselected **activation** does not consume its bearer. Unselected **refund enforcement** records the request for review, not an implemented denial. Unselected **cancellation accounting** records authoritative financial cancellation and pending-accounting review; it does not ignore/reject that cancellation or choose final counter/occupancy release.

`requestReturn` separates voluntary money request, physical receipt evidence, activation, usage and provider-confirmed reversal. Physical receipt alone cannot approve refund or delete membership. `src/lib/commerce/returns.ts:31-35` only tests check-in/redemptions for “used”: an activated but not checked-in unit falls into its unused branch and loses event occupancy today. That is not approved token-return policy and cannot be copied to the new model. With U3 late activation unselected, neither an unused past-event package nor missing check-in proves the perpetual token is unactivated or refundable. Preserve both facts and hold the disposition for review.

Cancellation policy fixtures must explicitly state independent deltas for paid purchase allowance, event committed capacity, event/account occupancy and token/recovery status. Test (a) the current-source-shaped release of remaining paid allowance and unused capacity/occupancy, and (b) a review-held accounting alternative; neither is selected product policy. Cite current `src/lib/commerce/reservations.ts:101-104`, `src/lib/commerce/reservations.ts:117-122`, not a claimed owner mandate to retain cancelled capacity. Never reset used benefits or erase original paid rows. Any irreversible token action remains separate.

While cancellation accounting is unresolved, retain original counters only as **temporary unreconciled evidence**, mark the affected allowance/capacity projections unavailable for new-sale/purchase-limit decisions, and hold those dependent operations for accounting review. Do not label cancelled units as final paid allowance or promise reusable capacity. The later production adapter must preserve authoritative cancellation, not roll it back for missing product policy; enabling live counter changes requires selected policy, schema and transaction proofs. Already submitted/confirmed issuance is reconciled under a financial hold, never treated as automatically undone. Money movement itself is absent from the fake kernel.
